# RECORD-002: `$PDK_ROOT`/`$PDK` token-substitution fix, re-verification

- **Slug**: `sg13cmos5l-divider-nrange-retiming`
- **Issue**: #61 (found while rebasing PR #60, which introduced this
  testbench directory, onto `main` after #43/PR #55 and #54/PR #58 had
  already fixed the identical bug twice in sibling directories)
- **What this record is**: a harness-level fix and its re-verification,
  **not** a new PVT campaign against the DUT. RECORD-001 remains the
  claim-under-test record for `divider_chain`'s functional `N` range and
  retiming margin; this record only asks whether RECORD-001's own numbers
  can be trusted given the bug described below, and appends new evidence
  where the answer needed a real re-run rather than an argument. Per
  `sim/README.md`'s append-only convention, RECORD-001 is **not** edited by
  this record.
- **Tooling**: `ngspice-46`, `PDK_ROOT=/home/ubuntu/share/pdk`,
  `PDK=ihp-sg13cmos5l` (the same real, installed PDK tree RECORD-001 used
  — not the synthetic `/tmp` PDK fixture some other repos in this
  environment use for unrelated tool tests).
- **Host contention**: this session shared its host with a concurrent,
  unrelated ngspice campaign running against a different in-progress
  Loom issue's own worktree (`sg13cmos5l-closed-loop-lock`, a different
  slug entirely) for a large part of the session. This is noted explicitly
  because it materially affected wall-clock timing for the `retime` stage
  below (see "The `fbfix`/top-of-band retiming-margin question"): the exact
  same corner, run in isolation, converged in ~100 real seconds twice in a
  row; the same corner run inside the full scripted campaign, competing for
  CPU with that concurrent job, hit the default 150 s budget instead. This
  is host-load variance, not a correctness regression, but it is exactly
  the kind of run-to-run variability RECORD-001 Finding 4 already flagged
  for this design's transients, and this record adds a directly-observed,
  attributable cause for it rather than leaving it anecdotal.

## The bug

All four `.sp.tmpl` decks under `../testbench/` (`tb_dff_hold`,
`tb_dff_setup`, `tb_div_func`, `tb_div_retime`), plus one heredoc-generated
deck inside `../testbench/run.sh` (the `opconv` stage, `run.sh:195` before
this fix — issue #61's own citation; the equivalent `echo ".lib ..."` line
has since shifted to `run.sh:282` post-fix, as this record's diff below
shows) — spelled the PDK model path into their `.lib`/`.include` lines as a literal
`$PDK_ROOT/$PDK` (or, in the heredoc, the double-escaped `\$PDK_ROOT/\$PDK`
needed to get a literal `$` into the generated file). ngspice's own
`.lib`/`.include` parser resolves such a `$VAR` **only** from ngspice's own
process environment — a `set` (not `export`)ed `PDK_ROOT` in the calling
shell is invisible to it. This is the exact bug #43 (PR #55) and #54
(PR #58) already fixed, twice, in every other testbench directory in this
repo; PR #60 introduced this directory's five decks before either fix had
landed, so they carried the same unfixed pattern.

**Direct demonstration, pre- and post-fix, same real PDK tree, same deck**
(`tb_div_retime.sp.tmpl` substituted for the `fbfix`/`mos_tt`/27 °C/3.3 V
top-of-band corner; the `.lib` line is the only difference between the two
files below):

$ # with every OTHER token but the literal `$PDK_ROOT/$PDK` left as-is, run

## The fix

1. All five sites now spell the path as `@PDK_ROOT@`/`@PDK@` tokens.
   `subst()` (`run.sh`'s shared per-template `sed` helper, used by all four
   `.sp.tmpl` decks) now appends `-e "s|@PDK_ROOT@|$PDK_ROOT|g" -e
   "s|@PDK@|$PDK|g"` to every substitution it does, once, in the helper
   itself — not repeated at each of the four call sites — so no future
   template added to this directory can forget it. The `opconv` stage's
   heredoc-generated deck isn't `sed`-templated (it's built line-by-line
   with bash `echo`), so its fix is the direct equivalent: `echo ".lib
   $PDK_ROOT/$PDK/..."` (bash-expanded, unescaped) instead of the old
   `echo ".lib \$PDK_ROOT/\$PDK/..."` (escaped, left for ngspice to resolve
   and unable to).

2. `runsp()`, the shared `ngspice -b` wrapper, previously discarded stderr
   (`2>/dev/null`) and swallowed every non-zero exit (`|| true`) — a fatal
   deck error (missing model, bad path, syntax error) was therefore
   indistinguishable from a corner that legitimately doesn't resolve, both
   showing up only as an unexplained `NA` row. `runsp()` now captures
   stderr and distinguishes a `timeout`-killed run (rc 124, or 137 if a
   `SIGTERM` didn't land in time) — the *documented, intentional* fate of
   the `opconv` stage's own hanging as-drawn `.op` analysis, RECORD-001
   Finding 1 — from every other non-zero exit, which is now treated as a
   fatal deck error: printed stderr, then the campaign aborts (`exit
   "$rc"`) instead of continuing with a silently-explained `NA`.

3. **`opconv` needed a different wrapper, not `runsp()`** — this is the one
   place the issue's own suggested-work text (written before this fix was
   attempted) undersold the problem. `opconv` isn't measuring whether a
   deck is well-formed; it's measuring whether the DUT's `.op` analysis
   converges at all, and a failed convergence (`Error: Transient op failed,
   timestep too small`, after gmin/source stepping both fail) is exactly
   the **result** this stage records, not a bug — `runsp()`'s new
   fatal-on-error behavior would turn that legitimate result into a
   campaign-ending abort. `runsp_opconv()` keeps the previous
   never-fatal contract (surfacing stderr instead of discarding it, but
   never aborting) and is used only by the `opconv` stage; `runsp()` (fatal
   on a real error) is used by `hold`/`setup`/`func`/`retime`, where a
   non-zero, non-timeout exit really does mean something is broken.

## A second, independent bug this fix's own re-verification found

Re-running `opconv` with stderr now visible surfaced a bug in the stage's
own convergence classifier, unrelated to the `$PDK_ROOT` pattern but living
in the same few lines: `elif echo "$log" | grep -qE "^divout\s"` was
checking for a print format ngspice never produces. The deck's own
`print v(divout) v(fb)` line makes ngspice echo back `v(divout) = <value>`
(and `v(fb) = <value>`) — never a bare `divout = <value>` — so the
`conv=yes` branch was **structurally unreachable**: every corner fell
through to the `else` (`conv=no`), regardless of whether OP had actually
converged. Fixed to `grep -qE "^v\(divout\)"`.

**This changes committed data.** RECORD-001 Finding 1 states "a bare `.op`
analysis on the whole chain... does not converge within 150 real
seconds... 4/4 rows: `converged=no`". Re-running with both fixes in place
(stderr visible, correct classifier) shows this is **only true for the
`asdrawn` variant** — `fbfix`'s OP genuinely converges (`Note: Dynamic gmin
stepping completed`, a real printed `v(divout)`/`v(fb)` value), and now
correctly reads `converged=yes` / `note=ok`. `asdrawn` still times out at
150 s in both re-runs below, `note=gmin stepping failed` — the pre-fix
`note` text (`no-message-before-timeout`) was itself wrong: stderr
discarding, not an actual absence of diagnostic text, is why it looked
uninformative; "gmin stepping failed" is emitted early (well before the
eventual 150 s kill during the final transient-op fallback, per
RECORD-001 Finding 1's own description of the failure sequence) and
survives a `timeout` kill just fine once it isn't thrown away.

`../corners/opconv.csv` is updated to the corrected values below (two full,
independent re-runs of the whole 4-row stage produced the same result both
times):

| variant | ic | converged (old→new) | note (old→new) |
|---|---|---|---|
| asdrawn | none | no → no | `no-message-before-timeout` → `gmin stepping failed` |
| asdrawn | applied | no → no | `no-message-before-timeout` → `gmin stepping failed` |
| fbfix | none | no → **yes** | `no-message-before-timeout` → `ok` |
| fbfix | applied | no → **yes** | `no-message-before-timeout` → `ok` |

**What this does and does not change about RECORD-001's own conclusions.**
It does not change Finding 1's bottom line for the *committed* design —
`asdrawn` still fails to reach an OP within the 150 s budget, at both
tested `.ic` settings, confirmed twice more here. It **does** correct the
record of `fbfix`'s own OP behavior: the proposal variant's operating point
is real and reachable, which is consistent with (not contradictory to) the
rest of RECORD-001 — Finding 2 already shows `fbfix` holds cleanly at the
rail in 9/9 corners, and Finding 4 already shows it divides by exactly
`N=64` at one calibration point, both of which require a converging OP to
begin with. The old `converged=no` row for `fbfix` was simply never a
correct measurement of anything; it is superseded by the corrected row
above, not by a re-interpretation of what "no" meant.

## The `fbfix`/top-of-band retiming-margin question (RECORD-001 Finding 5)

This is the specific question issue #61 asks this record to address:
RECORD-001's `insufficient-evidence` disposition for a numeric retiming-
margin bound rests on "6 real ngspice runs... did not reliably produce a
clean `DIVOUT`-to-next-VCO-edge... pair" — with stderr discarded at the
time, it was not possible to tell whether those were genuine convergence
difficulty or an unreported deck-load error (this issue's own bug) hiding
behind the same `NA`.

**This record answers that directly, from two independent angles:**

1. **None of RECORD-001's own supporting artifacts show the `$PDK_ROOT`
   error.** `../corners/manual-probes/retime-fbfix-tob-nominal-2p5x.log` and
   `retime-fbfix-tob-nominal-rise1-65ns.log` (both predate this fix) contain
   full, real ngspice transient traces — `Reference value:` lines through
   hundreds of timesteps, real node voltages, no `Cannot read environmental
   variable` anywhere in either file. A deck genuinely hitting the
   `$PDK_ROOT` bug fails **immediately**, at netlist load, before a single
   timestep — deterministically, on every attempt, in the same way. The
   documented behavior instead ("sometimes converged... sometimes did not
   complete within a 400–700 real-second budget", RECORD-001 Finding 4's
   own "tooling/reproducibility finding" about `func`'s baseline, which
   drove the same PVT-sweep session as `retime`) is stochastic and
   time-budget-dependent — the opposite signature. The 6 non-converging
   `retime` attempts are far more consistent with genuine numerical/
   compute-bound convergence difficulty on a 316-device transient than with
   a masked deck-load bug.

2. **A direct re-run, with the fix and with stderr surfaced, of the exact
   corner RECORD-001 Finding 5 discusses** (`fbfix`, `mos_tt`/27 °C/3.3 V,
   top-of-band 1562.0 MHz, the same 4.0×64-period window
   `../testbench/run.sh`'s current `retime` stage uses): built by hand from
   the same `subst()`-equivalent substitution `run.sh` performs (so the
   deck is byte-identical to what the scripted sweep generates for this
   corner), run twice, back to back, in isolation on an otherwise-idle host,
   each with a 150 s `timeout` cap and stderr captured to a file rather than
   discarded.

   **Both runs converged cleanly, in ~100 real seconds each** — well inside
   the 150 s default budget, not the 350–900 s RECORD-001's own manual
   probes needed at the smaller, pre-window-fix window sizes they tried.
   The two runs agree on every measured quantity to at least 6 significant
   figures:

   | run | `tdiv_s` | `tfb_s` | `dvo_max_v` | `fb_max_v` | `idd_a` |
   |---|---|---|---|---|---|
   | 1st (isolated host) | `1.077436e-07` | `1.086840e-07` | `3.601253e+00` | `3.424144e+00` | `-1.30760e-03` |
   | 2nd (isolated host, re-run) | `1.077436e-07` | `1.086840e-07` | `3.601253e+00` | `3.424144e+00` | `-1.30760e-03` |

   `fb_max` also matches RECORD-001's own pre-existing `fbfix-manual` row
   in `../corners/retime.csv` **exactly** (`3.424144e+00` in both), and
   `dvo_max` agrees to within 0.1% (`3.601253e+00` here vs `3.597767e+00`
   there — the small residual is consistent with the different window/
   `.tran` step RECORD-001's manual probe used, not a discrepancy this
   record needs to resolve). Both new runs additionally obtain the clean
   `tdiv`/`tfb` 50%-crossing timestamps RECORD-001's own manual probes never
   could — the specific number Finding 5 called `insufficient-evidence` for.
   Committed as `fbfix-manual-2` in `../corners/retime.csv` (RECORD-001's
   own `fbfix-manual` row is left untouched, per the append convention).

   **A third, independent data point sharpens rather than contradicts
   this**: the *same* corner, run inside the full scripted `retime` sweep
   above (competing for CPU with a concurrent, unrelated ngspice job on a
   shared host — see "Host contention"), hit the 150 s default budget and
   produced `NA` — indistinguishable, from the campaign's own output alone,
   from a genuine non-convergence. Run in isolation, twice, it converges
   comfortably inside the same 150 s window with room to spare. This is
   direct, first-hand confirmation of exactly the mechanism Finding 4 and
   Finding 5 already inferred indirectly ("sometimes converged... sometimes
   did not complete within a ... budget", "far more consistent with genuine
   numerical/compute-bound convergence difficulty... than with a masked
   deck-load bug") — this record did not have to infer it; it reproduced it
   directly, with an identified, attributable cause (host CPU contention)
   rather than an anonymous one.

**Disposition**: the fix **upgrades** RECORD-001 Finding 5's
`insufficient-evidence` disposition for this specific corner. A numeric
retiming-margin bound (`setup_avail = t(next CKIN_VCO edge) - t(DIVOUT
edge)`, `clk2q_frt = t(FB edge) - t(that capture edge)`) is now obtainable,
reproducibly, from `tdiv_s`/`tfb_s` above:

- `setup_avail = TPER - (tfb_s - tdiv_s) mod TPER` is not the right formula
  here without re-deriving which CKIN edge each of `tdiv`/`tfb` is actually
  measured against (`rise=2` on two different signals, not necessarily the
  same divide cycle) — this record deliberately does **not** compute a
  headline "X ps of margin" number from `tdiv_s`/`tfb_s` alone, because
  doing that derivation correctly is exactly the kind of interpretation
  step that deserves its own careful pass (and, ideally, its own PVT sweep
  once the host-contention confound above is controlled for), not a
  same-session afterthought bolted onto a testbench-infrastructure fix.
  What this record **does** establish is that the *inputs* to that
  derivation are now real, reproducible measurements instead of `NA` —
  the blocking question issue #61 asked this record to resolve.
- Finding 3's own qualitative conclusion ("the retiming margin at the
  measured top-of-band frequency is... inadequate for this specific
  weak-keeper sizing") is **not** contradicted by anything here — a clean
  `DIVOUT`-to-`FB` capture on THIS run does not by itself establish adequate
  margin; it establishes that the margin is now measurable. Reconciling
  the two (a numeric margin computation from `tdiv_s`/`tfb_s`, against
  Finding 3's setup-time requirement) is exactly the re-derivation flagged
  above, left to a future record so as not to expand this issue's own
  scope from "fix the testbench harness" to "re-litigate the retiming-
  margin claim."

## What was and wasn't re-verified

**Re-run to full completion, this record**: `opconv` (4/4 rows, 2 full
independent re-runs), `hold` (18/18 rows, full matrix), `retime` (18/18

**Not re-run in this pass**: `setup` (36 decks: 2 variants x 3 PVT bundles

already exercised without incident on `hold` and `retime` (same helper

tolerated-timeout classification), so there is no fix-specific reason to

silent gap. Re-running them is a natural next step for a future record,
not a blocker for this one: neither stage's committed numbers are touched
by anything in this record, so RECORD-001's own disposition for `setup`/

## Summary

- The `$PDK_ROOT`/`$PDK` unexpanded-path bug (issue #61) is fixed
  identically to the #43/#54 precedent: `@PDK_ROOT@`/`@PDK@` tokens in all
  five affected sites, substituted by `run.sh` before ngspice ever parses
  a deck.
- `runsp()` (the four scripted-measurement stages) now dies loud, with
  stderr, on a genuine ngspice failure, instead of silently degrading to
  `NA`; `runsp_opconv()` (the one stage that measures convergence *itself*)
  keeps the previous never-fatal contract but now surfaces stderr too —
  which is what exposed and let this record fix the second, independent
  `opconv` classifier bug (issue #61's own re-verification, not anticipated
  by the issue text).
- `opconv.csv` is corrected: `fbfix`'s DC operating point genuinely
  converges (`converged=yes`, `note=ok`), which the old classifier could
  never have reported regardless of the `$PDK_ROOT` bug.
- `hold.csv` reproduces byte-for-byte (18/18 rows); `retime.csv` gains its
  13 previously-missing rows (still `NA` for the reasons already on record)
  plus new, reproducible, converged evidence for the one `fbfix` corner
  RECORD-001 Finding 5 called `insufficient-evidence` — upgrading that
  disposition from "no clean measurement obtained" to "a clean measurement
  is obtainable and reproducible; deriving a numeric margin bound from it
  is left to a future record."
- `setup`/`func` are unchanged and not re-run; nothing in this record
  gives any reason to expect their committed numbers are wrong.

RECORD-001 remains the claim-under-test record and is not edited. This
record documents the harness fix, corrects `opconv.csv`, extends
`retime.csv`, and states explicitly what was and wasn't re-verified, per
`sim/README.md`'s append-only convention.
